## Arquitetura do frontend

Mesma disciplina de separar por responsabilidade que já uso no backend (routers/schemas/services) — componente nunca chama `fetch` direto, sempre passa por um service.

```
src/
├── pages/          # LandingPage, LoginPage, DashboardPage, SearchPage, RoadmapPage, AboutPage
├── components/     # reutilizáveis: MovieCard, Navbar, ChatBox, MessageBubble, SentimentBadge...
├── services/       # api/authService.js, api/filmsService.js, api/favoritesService.js
│                   #   -> único lugar com fetch() e header de auth centralizado
├── context/        # AuthContext.jsx -> evita repetir localStorage.getItem em tudo
├── hooks/          # useAuth.js, useWebSocket.js -> lógica reaproveitável
├── routes/         # ProtectedRoute.jsx
├── assets/
└── App.jsx
```

**Por quê:**

- Hoje a URL da API e o header `Authorization` estão espalhados e repetidos em cada função de `app.js`/`auth.js`. Centralizando em `services/`, muda-se a URL base ou a lógica de token num lugar só.
- Hoje cada página lê `localStorage.getItem('access_token')` na mão — se o token expirar, cada arquivo reage diferente. Com `AuthContext`, o estado de auth vive num lugar só.
